# 文档更新手法、报告模板与 Bootstrap 模式

Phase 3/4 的执行细则。所有编辑遵守 SKILL.md 硬约束 4（最小改动）与 7（数值只复制不默写）。

## 逐载体编辑手法

### 散文段落

1. 定位包含旧事实的**最小句子**；
2. 只替换句中的事实成分（数值、符号名、行为描述），保留主语结构、时态、语气与前后衔接；
3. 一句话陈述多个事实、只有一个变化时，不重写整句，只替换变化的成分；
4. 事实被彻底删除（功能下线）时删除对应句子；若删除导致段落逻辑断裂，做最小衔接修补并在报告中注明。

```
✗ 把 "The initial rule allows one to eight seats and closes booking thirty
   minutes before the event starts." 整句重写成自己的措辞
✓ 只把 "eight" 换成 "ten"，其余一字不动
```

### 表格

- 行级操作：新增行按表格既有排序规则插入（无明显规则则追加末尾）；删除行直接移除；修改只动变化的单元格。
- 不重排既有行序、不增删列（列结构变化是文档结构调整，超出同步范围，进报告）。
- 对齐用的空格差异不算改动，不要为对齐重排整表。

### Mermaid / PlantUML / 图源

- 只增删变更涉及的节点与边；新节点 id 沿用图内既有命名风格（如全大写缩写 `BOOK`、`PAY`）。
- 不改无关节点的声明顺序、不重排布局、不调整缩进风格——图源的 diff 应只显示净变化行。
- 时序图（sequenceDiagram）：流程步骤变化时只增删涉及的消息行；participant 增删要与消息行同步。
- 删除节点前确认它不再被任何边引用；删除事件边时发布与消费两条都要处理。
- 改完用 mermaid 语法校验（渲染器或语法检查）确认图仍有效。
- `.drawio` / 二进制导出图无法安全文本编辑：不直接改，列入报告并给出需要的变更描述。

### 代码示例与命令块

- 示例代码中引用的符号必须从当前公共入口可达，签名从当前代码复制。
- 命令、端口、路径、环境变量名从 `package.json` / compose / `.env.example` 当前内容复制。
- 示例整体已失效（API 重构）且无法机械替换时：不重写整个示例（那是创作不是同步），标 TODO 进报告。

### 目录树代码块

README/文档中的目录树按 `git ls-files` 的当前真实结构更新，只动变更涉及的行；树中省略号（`...`）代表的省略层级保持原省略策略。

### TODO 标记约定

需要人补充的位置插入：

```markdown
<!-- docs-sync: TODO(<类别>) <缺什么> ← <代码证据> -->
```

示例：`<!-- docs-sync: TODO(module-doc) waitlist 模块设计动机需人工补充 ← modules/waitlist/src/index.ts:1 -->`

每个 TODO 必须同时出现在同步报告的"建议但未动"节。禁止用 TODO 逃避可机械完成的替换。

## 同步报告模板

```markdown
# Docs Sync Report

## 锚点
- 变更集: <base>..<head>（或 工作区快照 @ <commit>）
- 文档集: <N> 篇（README <n> / docs <n> / 模块文档 <n> / 图源 <n>）
- 提取变更 <n> 条 → UPDATE <n> / ADD <n> / REPORT <n>

## 已更新
| # | 文档位置 | 旧 → 新 | 代码证据 | 意图来源 |
|---|---|---|---|---|
| 1 | docs/modules/booking.md:5 | "eight seats" → "ten seats" | booking-policy.ts:11 | commit abc123 |

## 建议但未动（ADD / REPORT）
| # | 变更 | 建议归属 | 缺什么 |
|---|---|---|---|
| 1 | 新模块 waitlist | docs/modules/waitlist.md（新建） | 设计动机需人工确认 |

## 漂移清单（既有问题，本次未修）
| # | 文档位置 | 失效引用 | 现状 |
|---|---|---|---|
| 1 | docs/core-flows.md:88 | `SendReceipt` | 代码中无此符号，疑为 SendPaymentReceipt 旧名 |

## 质疑项（如有）
- <新依赖边/行为删除与文档承诺的冲突，附双方证据，请人裁决>
```

小型变更（≤3 条更新、无 ADD/REPORT/漂移）可将报告压缩为对话内清单，但"文档位置 ← 代码证据"逐条对应不可省略。

## Bootstrap 模式（无文档基线时）

同步的前提是文档存在。仓库满足以下任一情形时，向用户确认后进入 bootstrap，而非在空集上硬做同步：

- 没有 `docs/` 且 README 只有安装说明；
- 模块文档覆盖率低于半数模块；
- 用户明确要求"从零建立文档"。

Bootstrap 步骤：

1. **建立事实清单** — 按 repository-understanding skill 的流程产出模块清单与关系边（该 skill 可用时直接调用其产物；不可用时按其 Phase 1/2 的最简版执行：workspace 声明定模块、公共入口定契约、import 图定依赖）。
2. **生成最小文档集** — 每模块一篇文档（职责 1–3 句 + 对外契约 + 上下游 + 数据所有权 + "不负责什么"），一篇架构文档（模块图 + 依赖规则 + 持久化所有权表）。只写有代码证据的行为事实，动机与背景全部留 TODO 标记。
3. **记录基线锚点** — 在架构文档头部注明 `<!-- docs-sync: baseline @ <commit> -->`，此后的增量同步以该锚点之后的 diff 为变更集。

Bootstrap 是一次性动作；完成后回到变更集驱动的常规同步，不得反复全量重建。

## 与既有 skill 的协作

- **repository-understanding**：Phase 2 的依赖边确认（"是否首次出现/完全消失"）与 bootstrap 的事实清单可复用其证据台账；本 skill 对代码同样只读，证据格式（`path:line`、[事实]/[推断] 分离）与其对齐。
- **graph-layout**：文档中的架构图若由图工具生成，mermaid 手改仅限简单增删；结构性重绘转交 graph-layout 的呈现层流程。
