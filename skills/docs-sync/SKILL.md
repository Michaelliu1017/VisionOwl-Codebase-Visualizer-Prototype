# Docs Sync

文档是代码的投影，不是并行的第二事实源。过期的文档比没有文档更糟——它以权威的口吻说谎。本 skill 让文档集追随代码事实：**变更多少，同步多少**；推不出来的，如实报告，留给人决策。

变更类别的判定细则见 `references/change-to-doc-mapping.md`；各类文档载体的编辑手法、报告模板与 bootstrap 模式见 `references/doc-update-playbook.md`。

## 八条硬约束

1. **代码是唯一事实源** — 文档与代码冲突时改文档，绝不为迁就文档改代码。若变更本身像 bug（如删掉了文档声称的核心行为），在报告中作为质疑项提出，但仍不动代码。
2. **只写文档载体** — 写权限仅限 README、docs/**、模块内 *.md、图源文件（mermaid/plantuml/drawio）。源码、测试、配置、CI 一律只读。
3. **变更集驱动** — 每次同步锚定一个明确 diff 范围（工作区 / staged / commit 区间 / 分支差）。不做全仓库文档大扫除，除非用户明确要求 bootstrap。
4. **最小改动** — 只更新能追溯到变更集的句子、表行、图边、示例。禁止顺手重写风格、重排结构、"优化"无关段落。diff 之外的文档问题只进报告，不动手。
5. **每处改动带证据** — 每一处文档修改都能指回 diff hunk 或代码 path:line；同步报告逐条列出"改了哪里 ← 因为代码哪里"。
6. **不臆造意图** — diff 只能证明"变成了什么"，不能证明"为什么"。原因与动机只能引自 commit message / PR 描述并标注来源；引不到就只陈述行为变化。
7. **数值与标识符只复制不默写** — 常量、路由、字段、命令、版本号一律从当前代码复制，不靠记忆，不从旧文档推算。
8. **漂移必须报告** — 匹配过程中发现的既有漂移（文档引用了不存在的符号/路径/行为），即使超出本次变更集不予修改，也必须列入漂移清单。

## 工作流

### Phase 0 — 锚定变更集

```bash
git rev-parse --short HEAD           # 同步锚点
git status --porcelain               # 工作区状态
git diff HEAD -M --stat              # 默认范围：未提交变更（-M 识别重命名）
git diff <base>...<head> -M --stat   # 用户指定区间 / 分支差
git log --format='%h %s' <range>     # 变更意图的唯一合法来源
```

范围优先级：用户指定 > 未提交变更（staged + unstaged）> 最近一次 commit。输出变更清单：`路径 + 状态(A/M/D/R) + hunk 概要`，并在报告开头声明锚点（commit 区间或"工作区快照 @ commit"）。变更集为空时直接结束，不进入后续阶段。

### Phase 1 — 提取文档可见变更

逐 hunk 判断是否"文档可见"。核心判据，满足其一即可见：

- 改变了模块**对外的承诺**（导出契约、路由、事件、业务规则）；
- 改变了系统**结构**（模块增删、依赖边、存储归属、部署单元）；
- 改变了人**执行操作的方式**（命令、配置、环境变量、启动步骤）。

三个都否——格式化、注释措辞、私有实现重构（导出面不变）、测试内部细节、依赖 patch 升级——是噪音，不触发文档更新。

| 变更类别 | 典型 diff 特征 | 通常影响的文档 |
|---|---|---|
| 导出契约 | 公共入口（index.ts 等）导出增删、公共签名变化 | 模块文档"对外契约"、README API 列表 |
| 业务规则常量 | 策略类/校验函数中的字面量、枚举、错误消息 | 模块文档中的规则句 |
| 路由 / 端点 | 路由注册的 method/path/payload 变化 | API 文档、流程时序图 |
| 事件契约 | 事件类型字段增删、发布/消费点变化 | 架构文档、发布与消费两侧模块文档、流程图 |
| 模块依赖边 | 跨包 import 首次出现或完全消失 | 架构图（mermaid）、依赖规则清单 |
| 模块生命周期 | workspace 成员增删、包重命名 | 架构图节点、模块文档目录、README 结构 |
| 存储 schema | DDL/migration、新表/列、缓存键格式 | 架构文档"持久化所有权"表 |
| 配置与环境 | .env.example、配置读取点增删 | README 运行说明、部署文档 |
| 命令与脚本 | package.json scripts、Dockerfile、compose | README 安装/运行/测试段 |
| 重命名 / 移动 | git -M 检出的 R 状态 | 所有引用旧路径的文档 |

每条提取的变更登记：`类别、代码证据（path:line 或 hunk）、旧事实 → 新事实`。识别细则与噪音清单见 `references/change-to-doc-mapping.md`。

### Phase 2 — 定位受影响文档

先建文档清单（一次 glob：`README*`、`docs/**`、`modules/**/*.md`、图源文件），再做双向匹配。

**正向（变更 → 文档）**，按四种线索在文档中检索：

1. **符号名** — 类/函数/事件/表名的字面出现（code span 与散文均算）；
2. **路径** — 文件/目录路径引用（含链接与目录树代码块）；
3. **字面量值** — 数值、枚举值在散文中的语言化形态（`8` ↔ "eight"，`30 * 60 * 1_000` ↔ "thirty minutes"）；
4. **图节点与边** — mermaid/plantuml 源中的节点 id、边、participant。

字面量的语言化匹配是漏报重灾区：数值改变时，必须在受影响模块的文档里同时检索数字形态与中英文数词形态。

**反向（文档 → 代码，漂移检测）**：对每篇被正向命中的文档，顺带验证其中引用的符号、路径、路由、命令在当前代码中仍存在；失效的记入漂移清单。

匹配结果三态：

- **UPDATE** — 文档中有对应位置 → 进 Phase 3 修改；
- **ADD** — 变更引入新概念（新模块/新事件/新配置），文档集中有明确归属处 → 新增最小小节或表行；
- **REPORT** — 找不到归属、或需要人的意图才能写（如新模块的设计动机）→ 只进报告，不落盘。

### Phase 3 — 执行最小更新

- **散文句**：定位含旧事实的最小句子，只替换事实成分，保留原句式与语气；
- **表格**：行级增删改，不重排既有列与行序；
- **mermaid / 图源**：只增删变更涉及的节点与边，沿用图内既有 id 命名风格，diff 应只显示净变化行；
- **代码示例与命令**：从当前代码复制真实内容替换，确认引用符号仍从公共入口可达；
- **重命名传播**：旧路径的所有文档引用逐一替换，包括链接目标与锚点。

不确定措辞时宁可保守：写行为事实，不写解释。需要人补充的位置插入 `<!-- docs-sync: TODO ... -->` 标记并列入报告。逐载体细则见 `references/doc-update-playbook.md`。

### Phase 4 — 交付同步报告

报告模板见 playbook，必含四节：

1. **锚点** — diff 范围、commit、文档集快照与命中统计；
2. **已更新** — 每条：文档 path:line ← 代码证据，旧 → 新，意图来源；
3. **建议但未动** — ADD/REPORT 项、建议归属位置、所缺信息；
4. **漂移清单** — 本次发现但未修的既有失效引用。

存在质疑项（新依赖边违反文档声明的依赖规则、变更疑似与文档承诺冲突）时增设第五节单独列出。

## 证据格式

示例取自 EventHub 仓库的演练场景（BookingPolicy 最大座位数 8 → 10；行号真实，变更与 commit 为演练示意）：

```
[变更] modules/booking/src/booking-policy.ts:11  quantity > 8 → quantity > 10
  类别 业务规则常量（BookingPolicy 校验阈值）
  影响 docs/modules/booking.md:5 "allows one to eight seats" → "allows one to ten seats"
  依据 文档句中的数词 eight 语言化对应 booking-policy.ts:11 的阈值字面量 8
  意图 commit <sha> "raise per-booking seat cap"（引用 commit message，非推断）
```

行号必须来自实际读取，禁止估算。同一旧事实在文档中出现多处（正文 + 表格 + 图）时，每处单独列一条，避免漏改。

## 交付前自检

- [ ] 本次全部文档改动都能指回变更集内的 hunk 或 path:line
- [ ] 未改动任何源码、测试、配置文件（git status 只出现文档路径）
- [ ] 变更集之外的段落零改动（无顺手重写）
- [ ] 数值、符号、路由、命令全部从当前代码复制核对
- [ ] 字面量的语言化形态（数词/时长）已检索并同步
- [ ] mermaid 图源改动后语法有效，节点/边引用一致
- [ ] 原因表述全部有 commit/PR 来源标注，无臆造动机
- [ ] 报告含锚点、已更新、未动项、漂移四节
- [ ] ADD/REPORT 项都给出归属建议与所缺信息

## 常见走样，逐条避免

| 走样 | 为什么错 | 正确做法 |
|---|---|---|
| 顺手重写整篇文档 | 抹掉人写的措辞与结构，评审无法聚焦 | 只改追溯到变更集的最小片段 |
| 从 diff 推断"为什么改" | 意图不是代码事实 | 只引 commit/PR 描述并标注来源 |
| 凭记忆写数值/命令 | 记忆会腐烂 | 从当前代码复制 |
| 只改数字不改数词 | "eight seats" 与 `8` 是同一事实 | 语言化形态一并检索替换 |
| 文档缺位就地发明设计动机 | 臆造 | ADD 只写行为事实，动机留 TODO |
| 漂移看见了不吭声 | 下次同步成本更高 | 即使不修也列入漂移清单 |
| 为文档一致性改代码 | 越权且方向颠倒 | 代码疑似 bug 时报告质疑 |
| 无锚点的全仓库文档大扫除 | 改动不可评审、不可追溯 | 锚定变更集；大扫除走 bootstrap 模式 |
| 更新图时重排全图布局 | 无关 diff 噪音淹没真实变化 | 只增删涉及的节点/边 |
| 只更新发布方文档，漏掉事件消费方 | 事件契约是两侧的承诺 | 发布与消费两侧文档都检查 |
