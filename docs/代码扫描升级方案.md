# 代码扫描升级方案

## 1. 背景

VisionOwl 当前采用“确定性 Scanner 生成图谱骨架，Agent 补充语义，校验后发布 GraphVersion”的架构。该架构具备 commit 绑定、证据追溯、AI 失败可回退等基础能力，但当前扫描器主要依赖目录、manifest 和 import 正则，对函数调用、路由、RPC、数据库、Redis、消息队列和跨仓库关系的识别不足。

本方案将扫描链路升级为：

源码解析 → Fact Index → 确定性图谱骨架 → Planner 拆分 → 模块 Agent 并行分析 → 受控 Patch → 全局综合 → 语义质量门禁 → 正式图谱版本。

## 2. 目标

1. 建立语言感知的 Fact Index，用结构化解析替代单纯正则推断。
2. 保留可复现的确定性骨架，同时允许 Agent 通过 graph-patch.json 提出可校验的图谱修正。
3. 将大型仓库拆成模块分析包，支持多 Runner 并行分析和局部重试。
4. 增加仓库级、Project 级全局综合，串联跨模块、跨仓库的关键业务流程。
5. 支持一个 Project 绑定多个仓库和分支，并将每个图谱版本绑定到明确的多仓库 commit 集合。
6. 建立语义质量门禁，从“JSON 合法”升级到“结构完整、证据有效、关系可信、流程连续”。
7. 保持增量分析能力，避免任何单仓库 Push 都引起全 Project 重扫。

## 3. 非目标

1. 首期不尝试训练或微调自有大模型。
2. 不允许 Agent 直接覆盖确定性图谱骨架。
3. 不依赖仓库名、服务名相似等弱证据自动建立正式跨仓库关系。
4. 不在一个 Runner 中默认挂载所有仓库全量源码。
5. 不为追求“图更丰富”而允许无证据的关系进入正式图谱。

## 4. 总体架构

### 4.1 分层

| 层级 | 职责 | 是否使用 AI |
|---|---|---|
| 源码解析层 | 语法树、类型系统、配置与协议解析 | 否 |
| Fact Index 层 | 统一表达模块、符号、入口、调用和资源事实 | 否 |
| 骨架层 | 从确定性事实生成可复现的 base graph | 否 |
| Planner 层 | 拆分模块、计算邻接、分配预算、生成分析包 | 首期否 |
| 模块分析层 | 理解模块职责、边界、风险和局部流程 | 是 |
| 全局综合层 | 串联跨模块、跨仓库流程，识别冲突与缺口 | 是 |
| Patch 校验层 | 校验 Agent 的增删改提案并生成 overlay | 以确定性为主 |
| 质量门禁层 | 评估覆盖率、证据、方向、流程连续性和稳定性 | 确定性 + 可选 AI Review |

### 4.2 运行流程

1. Cloud API 创建分析任务，记录 Project、Repository、Branch 和目标 commit。
2. Worker 将单仓库扫描任务交给 Scanner Runner。
3. Scanner Runner 输出 Fact Index、符号索引、接口目录、资源目录和确定性骨架。
4. Planner 根据骨架与模块边界生成 Analysis Packet。
5. Worker 按并发上限启动 Module Runner，每个 Runner 内运行一个 Qoder。
6. Module Runner 输出 Module Report 和 graph-patch.json，不直接修改 base graph。
7. Patch Validator 校验证据、符号、关系方向、commit 和 Schema。
8. Repository Synthesis Runner 基于通过校验的模块结果生成仓库级流程。
9. Cross-Repo Linker 根据 provides/requires 和服务身份目录生成跨仓库候选关系。
10. Project Synthesis Runner 串联跨仓库流程，只读取压缩后的分析产物和定向源码证据。
11. Semantic Gate 生成 quality-report.json，不合格部分进入局部重试。
12. 通过后生成正式 GraphVersion，更新 Project 当前图谱指针并发送 SSE 事件。

## 5. Fact Index 设计

### 5.1 解析策略

采用“Tree-sitter 广覆盖 + 语言专用解析器深解析 + 协议与配置 Parser”的组合方式。

| 对象 | 首选方式 | 首期提取范围 |
|---|---|---|
| JavaScript / TypeScript | TypeScript Compiler API + Tree-sitter 兜底 | import/export、类、函数、调用、路由、HTTP Client |
| Go | go/packages + go/ast + go/types | package、interface、function、call、HTTP/RPC、SQL/Redis |
| Python | Python ast + Tree-sitter 兜底 | module、class、function、import、call、route |
| Java | JavaParser/JDT + Maven/Gradle 解析 | module、class、interface、method、Spring Route、RPC |
| OpenAPI | OpenAPI Parser | method、path、schema、operationId |
| Protobuf / gRPC | Protobuf Parser | package、service、rpc、message |
| SQL / ORM | SQL Parser + 框架适配器 | table、read/write、migration、model |
| Redis | 调用模式 + 字面量解析 | command、key pattern、read/write |
| MQ | SDK 调用 + 配置解析 | topic、producer、consumer、event schema |
| 配置 | JSON/YAML/TOML/properties Parser | 环境变量、服务地址、队列、存储和部署单元 |

### 5.2 Parser Adapter 接口

每个语言解析器必须实现统一的 Adapter 契约，避免主扫描器与某种语言强绑定。

| 能力 | 输出 |
|---|---|
| detect | 是否支持当前仓库或文件 |
| parseFiles | 语法节点与基础证据 |
| resolveSymbols | 符号定义、引用和类型绑定 |
| extractInterfaces | HTTP、RPC、包、事件的 provides/requires |
| extractResources | DB、Redis、MQ、配置和外部服务 |
| diagnostics | 未解析符号、动态调用、缺失配置等不确定项 |

### 5.3 Fact 统一字段

| 字段 | 含义 |
|---|---|
| factId | 稳定的事实 ID |
| repositoryId | 事实所属仓库 |
| commitSha | 事实所属 commit |
| language | 来源语言或协议 |
| type | module、symbol、call、route、rpc、db、redis、mq、config 等 |
| subject | 事实主体 |
| relation | call、provide、require、read、write、publish、consume 等 |
| object | 事实对象 |
| evidence | 文件、行号、符号和摘要哈希 |
| extractor | 产生事实的 Parser 及版本 |
| certainty | exact、resolved、configured、unresolved |

### 5.4 Fact Index 产物

| 产物 | 用途 |
|---|---|
| facts.v2.json | 全部规范化事实 |
| symbol-index.json | 符号定义、引用和调用者快速定位 |
| interface-catalog.json | 对外 provides/requires，供跨仓库匹配 |
| resource-catalog.json | DB、Redis、MQ、配置和外部依赖 |
| diagnostics.json | 未解析、冲突和动态行为清单 |
| graph.base.json | 仅由确定性事实生成的不可变骨架 |

## 6. 确定性图谱骨架

1. 骨架只接受 Fact Index 输入，不调用 Agent。
2. 节点 ID 必须稳定，格式至少包含 repositoryId 和稳定路径或符号。
3. 所有非推断边必须指向 Fact ID 和源码证据。
4. graph.base.json 一旦生成不再就地修改，后续变化全部以 Patch 表达。
5. 无法解析的动态关系写入 diagnostics.json，不先行猜测建边。

## 7. Planner 与模块分析

### 7.1 模块边界优先级

Planner 按以下优先级识别模块：

1. workspace/package/module 显式声明。
2. Maven/Gradle/Go Module/Python package 等构建单元。
3. 独立部署单元与应用入口。
4. 框架模块声明。
5. 高内聚、低耦合的符号群。
6. 目录只作为最后兜底，不直接把普通文件夹当成业务模块。

### 7.2 Analysis Packet

每个模块产生一份可独立执行的分析包，包含：

- Project、Repository、Branch、Commit 和 Module ID。
- 模块入口、公共符号、关键路由、RPC 和消息消费入口。
- 一层上游、下游与资源依赖。
- 由 Fact Index 定位的精确源码片段，而不是任意截取整个文件。
- 增量模式下的 diff 和受影响符号。
- 模块级 token 预算、时间上限和要回答的标准问题。
- 输出 Schema 版本和所用 Skill 版本。

### 7.3 Module Runner

1. 每个 Analysis Packet 对应一个逻辑 Module Job。
2. Worker 根据 CPU、内存、仓库大小和成本预算控制并发，不无限启动容器。
3. 每个一次性 Runner 内启动一个 Qoder，只可见当前分析包授权的源码与产物。
4. Runner 输出 module-report.json 与 graph-patch.json，完成后销毁。
5. 未变化且输入哈希一致的 Analysis Packet 直接复用旧结果。

## 8. 受控图谱修正

### 8.1 graph-patch.json 操作

| 操作 | 用途 |
|---|---|
| add_node | 提议补充 Scanner 漏掉的真实节点 |
| add_edge | 补充有证据的调用、读写、发布或消费关系 |
| replace_edge | 修正关系类型或方向 |
| suppress_edge | 提议在最终 overlay 中屏蔽错误骨架边 |
| update_summary | 补充职责、边界与风险描述 |
| add_view | 增加关键业务流程或数据流视图 |

每个操作必须携带 baseGraphVersion、commitSha、source、target、type、reason、evidence、confidence、generator 和 skillVersion。

### 8.2 Patch 校验

| 校验 | 处理 |
|---|---|
| commit 不一致 | 直接拒绝 |
| 文件或行号不存在 | 直接拒绝 |
| 符号不在 Fact Index | 标记 unresolved，不合入正式事实 |
| 关系方向可由 call site 证实 | 作为 verified edge 合入 |
| 只有配置或间接证据 | 作为 configured/inferred edge 合入 |
| 和已有事实冲突 | 进入 conflict 清单，不静默覆盖 |
| 重复节点或边 | 去重并合并证据 |

合并时保留 graph.base.json、accepted-patches.json 和 rejected-patches.json，最终图谱为 base graph 与 accepted patch overlay 的组合结果。

## 9. 全局综合分析

### 9.1 Repository Synthesis Runner

每个仓库的模块分析通过后，启动一个仓库级综合 Runner。该 Runner 默认不重读全部源码，只读取：

- Fact Index 总览。
- 模块分析报告。
- 已通过校验的 Patch。
- 确定性模块关系。
- 候选关键流程及对应源码片段。
- diagnostics 中的冲突与未解析项。

它输出仓库级责任分层、业务流程、数据流、风险点和仓库级 Patch。

### 9.2 Project Synthesis Runner

多仓库 Project 需要再启动一个 Project 级综合 Runner，输入为：

- 各仓库的 Repository Report。
- 各仓库 interface-catalog.json。
- Cross-Repo Linker 的确定性关系和候选关系。
- 服务身份目录与人工确认的别名。
- 有疑问关系对应的定向证据片段。

该 Runner 负责串联跨仓库流程，不负责从头扫描每个仓库。如证据不足，它只能输出 targeted-read-request，由 Worker 补充指定仓库、模块和符号的上下文后再试。

## 10. 多仓库分析

### 10.1 数据模型

将当前“Project 只绑定一个 repository_binding”升级为：

| 对象 | 作用 |
|---|---|
| repositories | Project 内的仓库、分支、Provider、Installation 和仓库角色 |
| repository_snapshots | 某仓库某次分析使用的准确 commit |
| project_snapshots | 一次全局图谱所对应的 repositoryId → commitSha 映射 |
| service_identities | 服务的规范名、包名、路由、RPC、Topic 和别名 |
| cross_repo_edges | 跨仓库边、证据、匹配方式、状态与可信级别 |

graph_versions 需增加 project_snapshot_id、scanner_version、skill_version、quality_report_key 和 base_graph_key。

### 10.2 服务身份和关系匹配

每个仓库输出 provides 与 requires。Cross-Repo Linker 优先按以下证据匹配：

1. npm、Maven、Go Module 等确定包身份。
2. OpenAPI method/path/operationId。
3. Protobuf package/service/method。
4. Dubbo 等 RPC 接口全名。
5. Kafka、RocketMQ 等 Topic 与 Event Schema。
6. 配置中的服务发现名、URL 和人工确认别名。
7. 数据库表只表示共享数据依赖，不单独证明服务调用。

匹配结果分为 exact、configured、inferred 和 unresolved。只有 exact 和证据充足的 configured 关系可默认进入正式视图。

### 10.3 多仓库增量更新

单仓库 Push 后：

1. 只扫描改变的仓库和受影响模块。
2. 复用其它仓库已经绑定 commit 的分析产物。
3. 只重算与该仓库 provides/requires 有关的跨仓库关系。
4. 新建 Project Snapshot，其它仓库保留上一个已确认 commit。
5. 只重跑受影响的跨仓库关键流程和文档影响分析。

## 11. 语义质量门禁

### 11.1 指标

| 指标 | 定义 | 首期建议门槛 |
|---|---|---|
| 声明模块覆盖率 | 进入图谱的声明模块 / manifest 声明模块 | 100% |
| 关键入口覆盖率 | 已建模入口 / Parser 发现入口 | 不低于 95% |
| 证据可定位率 | 文件、行号、符号均可验证的证据 / 全部证据 | 100% |
| 无证据事实比例 | 未标 inferred 且无证据的结论 / 事实结论 | 0 |
| 确定性关系方向正确率 | 通过 call site/provider-consumer 验证的方向 / 可验证边 | 100% |
| 关键流程连续率 | 源、边、目标和证据连续的 step / 全部 step | 100% |
| 确定性重跑稳定率 | 同 commit 两次 base graph 一致性 | 100% |
| 语义结构重跑稳定率 | 同 commit 节点、关系、视图的结构相似度 | 不低于 98% |

门槛需通过基准集校准，不在未测试前作为永久常量写死。

### 11.2 门禁级别

| 级别 | 场景 | 行为 |
|---|---|---|
| hard_fail | Schema、commit、证据定位、悬空边、声明模块漏失 | 禁止发布 |
| retry | 入口覆盖不足、关键流程断裂、方向冲突 | 只重跑受影响模块或流程 |
| warning | 动态调用、反射、环境配置缺失、候选跨仓库别名 | 允许发布，但显示未解析警告 |

### 11.3 局部重试

1. Quality Gate 输出失败指标、Module ID、Fact ID 和证据缺口。
2. Planner 仅对失败范围生成 Retry Packet。
3. Retry Prompt 必须明确要检查的入口、关系或冲突，不重复完整任务。
4. 默认最多重试 2 次，仍失败则回退到 base graph，并将对应模块标记为 analysis_incomplete。

## 12. 任务与资源调度

将当前分析、Chat 和 Docgen 共用的队列逐步拆分，新增扫描升级任务类型：

| Stream | 任务 |
|---|---|
| scan:repo | 单仓库 Fact Index 与 base graph |
| analyze:module | 模块级 Qoder 分析 |
| synthesize:repo | 仓库级综合 |
| link:project | 跨仓库确定性匹配 |
| synthesize:project | Project 级综合 |
| quality:review | 质量门禁与局部重试 |

Worker 需要对每类任务设置独立并发上限、超时、重试和成本预算。模块并发任务必须使用 fan-out/fan-in 协调，只有必需模块达到终态后才能进入仓库综合。

## 13. 产物和版本

建议每个 Project Snapshot 保存以下产物：

| 范围 | 产物 |
|---|---|
| 单仓库 | facts.v2.json、symbol-index.json、interface-catalog.json、resource-catalog.json、graph.base.json、diagnostics.json |
| 单模块 | analysis-packet.json、module-report.json、graph-patch.json、module-quality.json |
| 仓库级 | repository-report.json、repository-views.json、accepted-patches.json |
| Project 级 | snapshot-manifest.json、cross-repo-links.json、unresolved-links.json、graph.final.json、quality-report.json |

每份产物必须记录 schemaVersion、scannerVersion、parserVersions、skillVersion、modelVersion、createdAt 和对应 commit 集合。

## 14. 对现有代码的改动

### 14.1 Scanner

- 将 cloud-backend/src/scanner/scan.ts 拆为 Scanner Orchestrator、Parser Registry、Fact Store、Symbol Resolver、Interface Extractor、Resource Extractor 和 Base Graph Builder。
- 保留 v1 Scanner 作为受控回退路径。
- 新建parsers/typescript、parsers/go、parsers/config、parsers/openapi 和 parsers/protobuf 等 Adapter。
- 新建facts/schema、facts/normalizer 和 facts/evidence 统一数据契约。

### 14.2 Graph 和 Validator

- 新增 graph-patch.schema.json、patchValidator.ts 和 patchMerger.ts。
- 将现有 graphValidator.ts 保留为结构校验器。
- 新增 semanticQuality.ts，输出 quality-report.json。
- GraphVersion 同时指向 base graph、accepted patches、final graph 和 quality report。

### 14.3 Worker 和 Runner

- 将 worker/analyze.ts 中的单次分析拆为 RepoScan、ModuleAnalyze、RepoSynthesize、ProjectLink、ProjectSynthesize 和 QualityReview。
- 将 Runner entrypoint 的巨型分支拆成独立 mode 脚本，每个 mode 只允许必需输入和输出。
- 增加 Planner 和 fan-out/fan-in 协调状态。
- 按 Analysis Packet 哈希缓存模块分析结果。

### 14.4 Skill

将当前单个 visionowl-graph Skill 拆分为明确职责：

| Skill | 职责 |
|---|---|
| visionowl-module-analysis | 单模块职责、边界、局部流程和 Patch |
| visionowl-repository-synthesis | 仓库级分层、流程与冲突 |
| visionowl-cross-repo | 跨仓库候选关系解释与定向证据请求 |
| visionowl-quality-review | 语义完整性检查，不修改图谱 |

### 14.5 Cloud API 与数据库

- 移除 repository_bindings.project_id 的单仓库唯一限制，增加 Project 多仓库 CRUD。
- Analysis Job 增加 repositoryId、projectSnapshotId、parentJobId、stage 和 retryOf。
- 新增 Project Snapshot、Service Identity、Cross-Repo Edge 和 Quality Result 相关表。
- Webhook 按 repositoryId/branch 定位受影响的 Project，并保留 delivery_id 幂等。
- API 增加仓库扫描状态、模块任务状态、质量报告和未解析关系查询。

### 14.6 前端

- Project 图谱按 Repository 绘制透明容器，节点保留 repositoryId。
- 跨仓库边显示匹配类型、可信级别和双方证据。
- inferred/unresolved 关系不与确定性关系使用相同视觉语义。
- 分析进度展示仓库扫描、模块分析、全局综合、质量校验和局部重试状态。

## 15. 执行阶段

### 阶段 0：建立基线

1. 准备单仓库、多语言和三仓库关联基准集。
2. 人工编制期望模块、入口、边、资源和关键流程。
3. 固化 v1 扫描产物、耗时、节点/边覆盖率和 Agent credits。
4. 建立重跑稳定性测试。

完成标准：已有可重复的 v1 质量和成本基线，升级后可做同集对比。

### 阶段 1：Fact Index v2

1. 定义 Fact Schema、Parser Adapter 契约和证据规范。
2. 首先实现 TypeScript/JavaScript、OpenAPI、Protobuf 和配置解析。
3. 实现符号定义/引用、HTTP 路由/Client、Redis、DB 和 MQ 事实。
4. 输出 Fact Index 与 diagnostics。
5. 保持 v1/v2 双跑，尚不切换正式图谱。

完成标准：声明模块覆盖 100%，证据可定位 100%，基准集的关键入口覆盖达到目标。

### 阶段 2：Base Graph 与 Patch

1. 从 Fact Index 生成 graph.base.json。
2. 定义 Graph Patch Schema 和 Patch Validator。
3. 调整 Agent，不再直接写最终 graph.json。
4. 实现 accepted/rejected/conflict 分类和 overlay 合并。
5. 用错误行号、错误方向、虚假符号和跨 commit 证据做拒绝测试。

完成标准：Agent 无法直接污染 base graph，所有最终语义变化均能追溯到 Patch 和证据。

### 阶段 3：模块化并行分析

1. 实现确定性 Planner 和 Analysis Packet。
2. Worker 支持 Module Job 的 fan-out/fan-in。
3. 新增 Module Runner mode 和 visionowl-module-analysis Skill。
4. 实现分析包哈希缓存和局部重试。
5. 实现 Repository Synthesis Runner。

完成标准：大仓库可分模块执行，单模块失败不要求全仓库重跑，仓库级关键流程可由模块结果组装。

### 阶段 4：语义质量门禁

1. 实现指标计算和 quality-report.json。
2. 区分 hard_fail、retry 和 warning。
3. 实现 Retry Packet 和最大重试次数。
4. 增加同 commit 双跑稳定性比较。
5. 将 Quality Gate 结果接入 GraphVersion 发布指针。

完成标准：未通过 hard gate 的图谱不会成为 Project 当前版本，失败原因可定位到仓库、模块、事实和证据。

### 阶段 5：多仓库图谱

1. 执行数据库迁移，支持 Project 多 Repository。
2. 实现 Project Snapshot 和多 commit manifest。
3. 实现 provides/requires 目录和 Cross-Repo Linker。
4. 实现 Service Identity 别名管理和未解析关系列表。
5. 实现 Project Synthesis Runner 和 visionowl-cross-repo Skill。
6. 接入单仓库 Push 触发的跨仓库增量重算。
7. 前端增加 Repository 分组、跨仓库边和 Snapshot commit 查看。

完成标准：三仓库基准集中的包依赖、HTTP/RPC 和 MQ 关系可被正确识别，任意一个仓库更新只重算必要范围。

### 阶段 6：灰度切换

1. 通过 SCANNER_VERSION=v1|v2 和 ANALYSIS_PIPELINE=v1|v2 特性开关控制。
2. 对指定 Project 双跑 v1/v2，v2 产物不立即替换当前图谱。
3. 对比质量、稳定性、耗时、credits、Runner 数量和容器资源。
4. 达标后按 Project 切换，保留 v1 回退能力一个完整发布周期。

## 16. 测试与验收

### 16.1 基准仓库

准备以下三类样本：

1. 单仓库 TypeScript 应用：包含 HTTP、PostgreSQL、Redis 和消息队列。
2. 多语言仓库：TypeScript API 调用 Go 服务，共享 Protobuf/OpenAPI。
3. 三仓库业务组：Order、Payment、Contracts，同时包含 HTTP、RPC 和 Topic 关系。

基准答案必须人工标注模块、入口、关系方向、资源和关键流程，不使用当前 Scanner 输出当作标准答案。

### 16.2 必测场景

- 模块、符号、路由、RPC、DB、Redis、Topic 的正常提取。
- 相对 import、别名 import、接口实现、跨 package 调用。
- 动态调用、反射和配置缺失被正确标记 unresolved。
- Agent 提交错误行号、不存在符号、错误方向和跨 commit 证据时被拒绝。
- 任一 Module Runner 超时后可局部重试，不重跑已通过模块。
- 全局综合发现冲突时生成 targeted-read-request。
- 同 commit 重跑 base graph 完全一致。
- 单仓库 Push 只更新受影响的仓库、模块和跨仓库边。
- 不通过 hard gate 的产物不切换正式 GraphVersion。

### 16.3 验收指标

| 类别 | 验收要求 |
|---|---|
| 准确性 | 达到第 11 节的质量门槛 |
| 可复现性 | 每份图谱均可追溯到完整 Project Snapshot |
| 安全性 | Runner 无长期 Token，不读未授权仓库，产物不包含密钥原文 |
| 增量性 | 单仓库局部修改不引起无关仓库和无关模块重跑 |
| 可观测性 | 可查看每阶段状态、耗时、credits、缓存命中、重试与门禁结果 |
| 可回退性 | 可按 Project 切回 v1 Scanner 和上一个通过门禁的 GraphVersion |

## 17. 性能与成本控制

1. Fact Index 以 repositoryId + commitSha + parserVersion 为缓存键。
2. Module Report 以 Analysis Packet 内容哈希 + skillVersion + modelVersion 为缓存键。
3. 模块文件未变更且直接依赖契约未变更时，复用上一次报告。
4. 仓库级综合只在模块报告或仓库公共契约变化时重跑。
5. Project 级综合只在跨仓库关系、仓库职责或关键流程变化时重跑。
6. Quality Gate 失败后只重跑失败范围，不进行全量 Agent 重试。
7. 并发度根据容器内存、CPU、当日 credits 预算和任务优先级动态调整。

## 18. 安全边界

1. Scanner Runner 默认只读单个仓库的精确 commit。
2. Module Runner 只读 Analysis Packet 允许的路径与只读产物。
3. Project Synthesis Runner 默认只读取脱敏的仓库报告和定向证据，不挂载全部源码。
4. GitHub App Installation Token 必须是短期 Token，不写入产物和数据库。
5. evidence 只保存文件、行号、符号与必要摘要，并继续执行密钥打码和长度上限。
6. 跨仓库读取必须同时通过 Project 成员权限和 Repository Installation 权限。
7. 不将某 Project 的未脱敏事实、Patch 或源码证据作为其它 Project 的模型上下文。

## 19. 风险与对策

| 风险 | 对策 |
|---|---|
| 语言和框架种类过多 | Parser Adapter 插件化，先覆盖主要语言和基准仓库 |
| 动态调用无法静态确定 | 输出 unresolved，后续可接运行时 Trace，不强行建确定边 |
| 模块拆分过粗或过细 | 优先显式构建边界，增加 Planner 诊断和人工 override |
| 并行 Agent 结果冲突 | 统一 ID、Schema 和 Patch，由综合层报告冲突，不用后写覆盖 |
| 多仓库别名匹配错误 | 建立 Service Identity Catalog，区分 exact/configured/inferred |
| Runner 数量导致资源和 credits 上升 | 任务缓存、动态并发、分层预算和局部重试 |
| 质量门槛过严导致无法发布 | hard/soft 分级，用基准集校准，允许携 warning 发布 |
| v2 出现回归 | v1/v2 双跑、Project 级开关、GraphVersion 指针回退 |

## 20. 推荐的首个实现批次

首个批次只处理 TypeScript/JavaScript 单仓库，但 Schema 和 ID 从第一天就携带 repositoryId，避免后续为多仓库重构。

首批交付顺序：

1. Fact Schema 和 Parser Adapter 契约。
2. TypeScript Compiler API 提取 module/symbol/call/import/export。
3. HTTP route/client、PostgreSQL、Redis 和 MQ 事实提取。
4. facts.v2.json、symbol-index.json 和 graph.base.json。
5. Graph Patch Schema、Validator 和 Merger。
6. 单模块 Analysis Packet 和 Module Runner。
7. 模块级证据可定位率、入口覆盖率和无证据事实门禁。
8. v1/v2 基准对比报告。

该批次验证通过后，再增加 Go Adapter、多模块并行、仓库级综合和多仓库关系装配。
