# VisionOwl 产品演示闭环修复方案

> 日期：2026-08-05  
> 状态：待确认，尚未开始修改业务代码  
> 目标：用最小但真实的实现，跑通“桌面端选择公开仓库 → 云端分析 → 实时更新 → Push 增量分析 → 文档更新 → Qoder 对话与一键文档生成”的完整演示闭环。

## 1. 本次演示边界

### 1.1 必须实现

1. 用户在 Electron 桌面端登录并创建 Project。
2. 用户输入或选择一个公开 GitHub 仓库，并从真实分支列表中选择目标分支。
3. 用户明确点击“开始分析”。
4. Cloud API 创建 full job，写入 PostgreSQL，并通过 Redis Stream 投递。
5. Worker 消费任务并启动一次性 Runner。
6. Runner 克隆目标仓库并 checkout 精确 commit，执行确定性扫描、Qoder CLI 和 `visionowl-graph` Skill。
7. 完整 `graph.json`、`impact.json`、架构文档和生成文档进入 OSS；PostgreSQL 保存任务、图谱版本、当前版本和文档索引。
8. Electron 接收 SSE 进度，分析完成后下载 `graph.json`，校验后在本地解析和渲染。
9. 向已监听分支 Push 后，Webhook 验签并创建 incremental job。
10. Electron 立即显示“检测到代码变更 / 分析变更中”窗口，持续显示真实进度。
11. 增量分析完成后，Electron 自动切到最新 commit 的图谱并刷新文档，无需手动刷新。
12. 选中模块后，可以在 Agent 窗口向云端 Qoder 提问，并得到带代码证据和图上高亮动作的回答。
13. 点击“生成文档”快捷按钮，触发真实 Qoder 文档任务，完成后在桌面端直接查看生成的 Markdown 文档。

### 1.2 为尽快演示，本轮不做

- 私有仓库和完整 GitHub App 安装流程。
- 任意公开仓库自动创建 GitHub Webhook。演示仓库由仓库管理员预先配置一次 Webhook。
- 团队邀请、角色管理和多客户端协作演示。
- 图谱历史版本管理 UI、回滚 UI、审计日志 UI。
- 钉钉开放平台写文档；本轮生成平台内 Markdown 文档。
- 桌面安装包自动更新和生产级多地域容灾。

## 2. 目标闭环

```text
Electron
  ├─ 创建 Project
  ├─ 查询公开仓库与分支
  ├─ 绑定 repo@branch
  └─ 点击开始分析
        ↓ REST
Cloud API
  ├─ 校验 repo@branch 并解析 branch HEAD SHA
  ├─ PostgreSQL 创建 full job
  └─ XADD Redis Stream
        ↓
Worker
  ├─ XREADGROUP 消费
  ├─ 获取带所有权的分布式锁
  └─ docker run 一次性 Runner
        ↓
Runner
  ├─ clone + checkout 精确 SHA
  ├─ scanner → facts.json / graph 骨架 / impact.json
  ├─ qodercli + visionowl-graph Skill → 语义增强
  └─ Schema 校验
        ↓
Storage
  ├─ OSS：graph / impact / architecture / module docs
  └─ RDS PostgreSQL：job / graph version / document metadata
        ↓ SSE
Electron
  ├─ 实时任务窗口
  ├─ 下载和校验 graph.json
  ├─ 本地渲染图谱
  └─ 刷新最新文档

GitHub Push
  → signed webhook
  → latest-SHA incremental job
  → 相同 Worker/Runner/Storage/SSE 链路
  → Electron 自动切换到新图谱和新文档
```

## 3. 审计结论

当前系统不是从零开始：Redis、Worker、Runner、Qoder 图谱分析、图谱渲染和 Webhook 主体都已经存在，ECS 上也有成功任务记录。但用户要求的演示闭环尚未闭合。

### 3.1 当前运行态

| 项目 | 当前状态 | 与目标差异 |
|---|---|---|
| Cloud / Worker / Gateway | ECS 容器正在运行 | 可复用 |
| Redis | 容器健康 | 可复用，但无持久化和 pending reclaim |
| Analyzer | `runner` | 符合目标 |
| Qoder | Worker 已配置 PAT | 图谱分析可用，Chat 尚未使用 Qoder |
| GitHub Webhook secret | 已配置 | 演示仓库仍需在 GitHub 手工配置 Webhook |
| GitHub App | 未配置 | 本轮只演示公开仓库，不阻塞 |
| PostgreSQL | ECS Compose 内的 `postgres` 容器 | 不是 RDS |
| Artifact | `/data/artifacts` 本地目录 | 不是 OSS |
| 本地仓库与部署源码 | 8 个核心后端文件不同 | 必须先消除源码漂移 |

### 3.2 按演示步骤检查

| 演示步骤 | 已有实现 | 缺陷或不同点 | 本轮处理 |
|---|---|---|---|
| 创建 Project | 已实现 | 无明显阻塞 | 保留并补错误反馈 |
| 选择公开仓库 | 仅自由文本输入 | 不查询 GitHub，无法确认仓库是否公开/存在 | 增加公开仓库解析接口和 UI 校验 |
| 选择分支 | 仅自由文本输入，默认 `main` | 不拉真实分支列表，错误分支要等 Runner 才失败 | 增加分支列表 API 和下拉框 |
| 绑定后点击分析 | 当前“绑定并开始分析”自动触发 | 与演示步骤不一致，失败边界不清晰 | 绑定成功后显示明确“开始分析”动作 |
| 创建 full job | 已实现 | 公开仓库无法在建任务时解析 HEAD SHA，job target SHA 可能为空 | 服务端解析公开分支 HEAD 后再创建任务 |
| Redis 投递 | 已实现 `XADD` | 入队失败靠巡检，Stream pending 消息不回收 | 增加 pending reclaim 和幂等处理 |
| Worker 消费 | 已实现 `XREADGROUP` | 未获得锁也会删除他人锁 | 改为 ownership token + compare-and-delete |
| Runner 启动 | 已实现 | Git 仓库源码与线上修复版有漂移 | 先合并线上 Runner 修复 |
| 精确 commit | 有 checkout | checkout 失败会静默使用分支 HEAD | 有目标 SHA 时必须 checkout 成功，否则任务失败 |
| Qoder + Skill 图谱分析 | 已实现 | 本地仓库版 Runner 缺少线上已有的环境导出等修复 | 合并并增加产物完整性校验 |
| 增量分析 | 能产生 diff/impact | 扫描仍重建全图；Qoder 未严格限制到影响模块；连续 Push 可能丢最新 SHA | 保持“完整图重建”保证正确性，限制 Qoder 上下文并修复 latest-wins 去抖 |
| PostgreSQL | job/version/doc 索引已落库 | 当前是 ECS 本地容器，不是 RDS | 切换生产 `DATABASE_URL` 到 RDS 并执行迁移 |
| OSS | 无 | `artifact_oss_key` 实际指向 ECS 本地文件 | 引入 OSS ArtifactStore，生产强制使用 OSS |
| 图谱下载 | REST artifact 端点已实现 | 当前从本地磁盘读取 | 改为从 OSS 读取或 302 到短时签名 URL |
| 首次分析进度 | 桌面端轮询自己创建的 job | 单全局 timer、重启无法恢复 | 统一改用项目 SSE，并在启动时恢复活跃任务 |
| Push 触发增量任务 | Webhook 已实现 | 仓库 Webhook 不会因桌面绑定自动出现 | 演示仓库预配置；桌面显示监听状态说明 |
| Push 后立即弹窗 | 未实现 | 桌面端不订阅 `/events`，完全不知道 Webhook job | 接入 SSE，收到 incremental `job.created` 立刻弹窗 |
| 新图谱自动刷新 | 未实现 | 仅手动任务轮询成功后刷新 | 收到 `graph.version.switched` 后自动拉取和校验 |
| 文档自动更新 | 线上漂移版会更新全局架构文档、标记模块文档 stale | Git 仓库没有这些实现；桌面不会实时刷新 | 合并线上实现，并自动刷新已生成的受影响模块文档 |
| 查看生成文档 | 后端线上版有 content API | 桌面把 `visionowl://` 当外链，Electron 会拒绝打开 | 改为应用内 Markdown 查看器 |
| Agent 模块问答 | UI 和 SSE 格式存在 | 后端是规则拼接，明确没有调用 Qoder | 增加真实 Qoder chat provider，规则回答仅作为降级 |
| Agent 多轮会话 | 后端支持 sessionId | 桌面每次固定传 `null` | 保存 `chat.meta.sessionId` 并带到下一轮 |
| 一键生成文档 | 按钮存在 | 只是发送“生成文档”聊天提示词 | 改为调用 docgen API、显示状态并刷新文档 |

## 4. 必须先解决的源码问题

### 4.1 建立唯一源码

开发和部署都以本地 Git 仓库为唯一来源：

```text
本地修改 → 本地测试 → Git diff 审核 → 构建不可变镜像 → ECS 部署
```

不继续直接修改 `/opt/vo/cloud-backend`。当前 `/opt/vo` 中已经存在但未回到 Git 的能力包括：

- 全局架构文档自动生成与更新。
- 单模块 docgen API、Redis 任务和 Runner 模式。
- generated 文档内容读取接口。
- 图谱 current 切换和同 SHA 复用修复。
- Runner 输出目录环境变量修复。

实施第一步是逐文件合并这些差异，保留正确修复并补测试。不会直接用整个部署目录覆盖仓库。

### 4.2 清理迁移污染文件

删除 `cloud-backend/migrations/._001_init.sql`。当前迁移器会执行所有 `.sql` 文件，该 AppleDouble 文件可能导致下一次迁移失败。

## 5. 分阶段修复方案

### 阶段 A：公开仓库绑定与首次分析

#### A1. 云端公开 GitHub 查询

新增只读接口：

```text
GET /api/github/public/repos/:owner/:repo
GET /api/github/public/repos/:owner/:repo/branches
```

职责：

- 通过 GitHub REST API 验证仓库存在且为 public。
- 返回 repository id、default branch、分支列表。
- 对 GitHub 失败、限流和仓库不存在返回明确错误。
- 绑定时服务端再次校验，不能只信桌面端。

#### A2. 桌面绑定流程

修改 Project 创建弹窗：

1. 创建 Project。
2. 输入 `owner/repo` 或 GitHub URL。
3. 点击“检查仓库”。
4. 从后端返回的真实分支列表选择分支。
5. 点击“绑定仓库”。
6. 绑定成功后显示“开始分析”按钮。

#### A3. full job 精确 SHA

- Cloud API 在创建 full job 前解析公开分支 HEAD SHA。
- `target_commit_sha` 必须在入队前写入数据库。
- Runner 必须 checkout 该 SHA；失败时任务失败，不允许静默改用其他 HEAD。
- 完成时校验 `job.targetCommitSha == graph.commitSha == graph_versions.commit_sha`。

### 阶段 B：队列、Worker 与 Runner 可靠性

#### B1. 分布式锁

- 获取锁时写入随机 ownership token。
- 只有 token 匹配的 Worker 才能通过 Lua compare-and-delete 释放锁。
- 未获得锁的消息可以 ACK，但不能删除现有锁。

#### B2. Redis Stream 恢复

- Worker 启动和定时巡检使用 `XAUTOCLAIM` 回收超时 pending 消息。
- PostgreSQL job 状态继续作为最终幂等依据。
- 演示期间启用 Redis AOF，避免 Redis 重启后队列和 docgen 状态全部消失。

#### B3. Runner 产物契约

必须存在并通过检查：

```text
graph.json
facts.json
meta.json
impact.json          # incremental 时
ARCHITECTURE.md      # full/incremental 均生成或确定性兜底
```

Qoder 失败时：

- 图谱可以回退确定性骨架，但任务日志和图谱元数据必须标明 `semanticEnhanced=false`。
- 演示 UI 必须能区分“完整 Qoder 分析”和“仅确定性扫描”，不能假装成功使用了 Qoder。

#### B4. 增量策略

演示版本采用“正确性优先”：

- 每次 Push 仍生成一份新的完整图谱版本，避免局部 patch 造成旧节点残留。
- `git diff` 只用于影响面和限制 Qoder 读取范围。
- Qoder 输入显式包含 changed files、affected nodes 和邻接闭包。
- 对已存在的受影响 generated 模块文档触发刷新；普通外链文档只标记 `maybe_stale`。

### 阶段 C：RDS 与 OSS

#### C1. RDS

`pg` 客户端本身可连接 RDS，主要改动是部署配置：

- 生产环境 `DATABASE_URL` 指向 RDS 内网地址。
- 执行现有迁移并核对表、索引和当前版本外键。
- 在切换前备份 ECS 本地 PostgreSQL。
- Compose 中本地 PostgreSQL 保留为开发 profile，不再作为生产依赖。

前置条件：已创建可从 ECS 内网访问的 RDS PostgreSQL，并提供数据库名、账号和连接地址。

#### C2. OSS ArtifactStore

新增统一接口：

```ts
interface ArtifactStore {
  put(key: string, body: Buffer | string, contentType: string): Promise<void>
  get(key: string): Promise<Buffer>
  exists(key: string): Promise<boolean>
}
```

实现：

- `LocalArtifactStore`：仅本地开发和测试使用。
- `OssArtifactStore`：生产使用阿里云 OSS SDK。
- 生产环境缺少 OSS 配置时启动失败，避免误把本地磁盘当 OSS。

对象 key：

```text
visionowl/{projectId}/{commitSha}/graph.json
visionowl/{projectId}/{commitSha}/facts.json
visionowl/{projectId}/{commitSha}/impact.json
visionowl/{projectId}/{commitSha}/ARCHITECTURE.md
visionowl/{projectId}/{commitSha}/modules/{safeNodeId}.md
```

PostgreSQL 只保存对象 key、版本、commit、统计和文档索引，不保存完整图谱正文。

桌面端仍通过 Cloud API 下载，Cloud API 从 OSS 读取后返回；这样不会把 OSS 长期凭证暴露给客户端。

前置条件：已创建 OSS bucket，并提供 ECS 可用的 RAM 权限或 AccessKey、endpoint 和 bucket 名。

### 阶段 D：桌面 SSE 与变更分析窗口

#### D1. 项目事件客户端

新增通用 SSE parser，使用 `fetch` 而不是原生 EventSource：

- 通过 `Authorization: Bearer` 发送 token，避免 token 出现在 URL。
- 记录 `Last-Event-ID`。
- 网络中断指数退避重连。
- 切换 Project 或退出登录时主动取消旧连接。

#### D2. 事件状态机

| 事件 | 桌面动作 |
|---|---|
| `repository.push.received` | 立即弹出“检测到代码变更”，显示 repo、branch、before/head SHA |
| `job.created` | 设置当前项目 job；若为 incremental，立刻弹出“检测到代码变更”窗口 |
| `job.progress` | 更新进度、阶段文案和窗口进度条 |
| `job.failed` | 显示失败原因和重试入口 |
| `job.succeeded` | 显示 credits，等待或配合 graph switched |
| `graph.version.switched` | 拉取 current version 和 artifact，校验 commit 后原子替换图谱 |
| `document.created/updated/deleted` | 重新拉取项目文档 |

#### D3. 启动恢复

- 进入 Project 时调用 `GET /projects/:id/jobs?limit=1`。
- 若最新任务为 queued/running，恢复进度窗口。
- SSE 事件只作为通知，最终状态始终通过 REST 拉取确认。
- 删除全局单例 `pollTimer`，避免项目切换后错误刷新旧 Project。

#### D4. 变更窗口

新增轻量模态窗口：

```text
检测到目标分支新提交
repo @ branch
oldSha → newSha
排队中 / 克隆 / 扫描 / Qoder 分析 / 保存 / 更新文档
```

任务完成后显示新图谱版本和 commit，自动刷新画布；用户可点击关闭。

### 阶段 E：Webhook latest-wins

#### E1. 演示仓库配置

由于本轮不做 GitHub App，必须在演示仓库 GitHub Settings 中预配置：

```text
Payload URL: <Cloud Public URL>/webhook/github
Content type: application/json
Secret: 与 ECS GITHUB_WEBHOOK_SECRET 一致
Events: Just the push event
```

桌面绑定任意公开仓库只能保证“可分析”，不能保证该仓库已配置 Webhook。演示脚本必须使用受控仓库。

#### E2. 去抖修复

当前逻辑会在 30 秒窗口内直接返回旧任务，可能丢掉最新 SHA。改为 latest-wins：

- 每次 Push 都更新 `pending:{projectId}` 中的 latest head/base/delivery。
- 首次 Push 安排一个延迟 flush。
- 窗口结束后只为最新 SHA 创建一个 incremental job。
- 如果窗口期间没有第二次 Push，可立即创建或在短窗口后创建；桌面先收到 `repository.push.received` 或 job pending 提示。
- dedup key 继续保证相同 SHA 不重复分析。

对于单次 Push 演示，窗口应尽量短，并确保桌面在数秒内出现反馈。

### 阶段 F：文档更新与一键生成

#### F1. 合并线上 docgen

将部署快照中的以下能力正式合入 Git：

- `POST /projects/:id/documents/generate`
- `GET /projects/:id/docgen/:taskId`
- `GET /projects/:id/documents/:docId/content`
- Redis docgen 消息类型和状态。
- Worker `processDocgen`。
- Runner `RUN_MODE=docgen`。
- `upsertGeneratedDoc`。

#### F2. 修复 docgen 一致性

- docgen 必须 checkout 当前图谱对应的 commit，而不是运行时分支最新 HEAD。
- 文档对象 key 必须包含 commit SHA，不能覆盖无版本固定 key。
- 更新 generated 文档前创建 revision。
- docgen 失败不创建空文档，并向桌面返回错误。

#### F3. Push 后文档行为

- 每次分析更新全局 `ARCHITECTURE.md`。
- 外链/钉钉文档：受影响时标记 `maybe_stale`。
- 已存在的 generated 模块文档：受影响时自动排队重新生成，成功后恢复 `ok`。
- `document.updated` 事件通知桌面刷新。

#### F4. 桌面文档体验

- “生成文档”快捷按钮不再走 Chat，而是调用 docgen API。
- 显示“排队 / 生成中 / 完成 / 失败”。
- 完成后自动切换到文档 tab。
- generated 文档通过 content API 拉取，在应用内只读 Markdown 面板展示。
- 外部 HTTP/HTTPS 文档继续交给系统浏览器。

### 阶段 G：真实 Qoder Agent Chat

#### G1. 当前问题

当前 `services/chat.ts` 是规则匹配和图邻接拼接，`credits=0`，没有调用 Qoder。桌面端还把每次 `sessionId` 固定为 `null`，因此没有真实多轮会话。

#### G2. 演示实现

在 Cloud 侧增加 Qoder Chat Provider：

1. 读取当前 graph version、选中节点、两层邻接、evidence、最近 impact、关联文档和最近会话。
2. 生成受限上下文，不把完整仓库发送给 Chat。
3. 调用云端 `qodercli`，要求返回严格 JSON：

```json
{
  "answer": "...",
  "evidence": [],
  "nodeIds": [],
  "edgeIds": [],
  "inferred": false
}
```

4. 服务端校验 evidence、nodeId 和 edgeId 都属于当前图谱。
5. 通过现有 Chat SSE 协议发送 `meta/delta/evidence/action/done`。
6. 保存用户问题和最终回答；桌面保存 `sessionId`，后续问题继续同一会话。

为减少演示风险：

- Qoder 超时或结构化输出失败时，可降级到现有规则回答。
- UI 必须显示“Qoder”或“规则降级”，不能把降级回答伪装成 Qoder。
- 单轮设置独立超时和较低 max-turns，避免拖慢演示。

## 8. 测试与验收

### 8.1 后端自动测试

- 公开仓库 URL 解析、仓库/分支不存在、GitHub 限流。
- full job target SHA 固定和 dedup。
- Webhook 验签、delivery 幂等、目标分支过滤。
- 连续 Push latest-wins，不丢最后一个 SHA。
- Worker 锁只能由 owner 释放。
- Stream pending 消息可以 reclaim。
- graph/impact/document OSS key 与 RDS 索引一致。
- generated 文档 revision 与 commit 对齐。
- Qoder Chat 输出校验和规则降级。

### 8.2 桌面端验证

- 创建项目后可查询公开仓库和真实分支。
- full job 进度由 SSE 驱动，不依赖手动轮询。
- 重启应用后恢复运行中的任务。
- incremental `job.created` 会立即弹出变更窗口。
- `graph.version.switched` 后自动更新 graph、SHA、views、documents。
- generated 文档在应用内打开。
- Agent 选中节点、证据展示、图上高亮和多轮 session 正常。

### 8.3 最终演示脚本

1. 启动已连接真实 Cloud API 的 Electron。
2. 登录演示账号。
3. 创建新 Project。
4. 输入受控公开仓库，加载并选择目标分支。
5. 绑定并点击“开始分析”。
6. 展示 Redis queued、Worker running、Runner Qoder 阶段和实时进度。
7. 任务成功后展示：
   - RDS 中的 succeeded job 和 graph version。
   - OSS 中对应 commit 的 graph/impact/architecture 对象。
   - Electron 自动下载并渲染图谱。
8. 选中一个模块，点击“生成文档”，等待完成并在应用内打开。
9. 在同一模块 Agent 窗口提问，展示 Qoder 回答、evidence 和图上高亮。
10. 修改演示仓库中该模块并 Push 到目标分支。
11. Electron 无需操作，自动弹出“检测到代码变更”。
12. 展示 incremental job、影响模块和文档更新状态。
13. 完成后确认：
   - 新图谱 commit SHA 等于 Push head SHA。
   - 图谱自动切换。
   - 全局架构文档已更新。
   - 受影响 generated 模块文档已更新或明确显示生成状态。

### 8.4 演示通过条件

- 从点击分析到图谱显示，全程不手动刷新数据库、容器或桌面应用。
- 从 GitHub Push 到桌面出现变更提示，不超过 10 秒。
- Push 后 60 秒内出现 incremental job；实际完成时间取决于仓库大小和 Qoder。
- `push head SHA == job target SHA == graph version SHA == graph.json SHA`。
- 图谱和生成文档均能从 OSS key 追溯到同一 commit。
- Agent 回答明确标识 Qoder 或降级来源，并展示有效 evidence。

## 9. 部署与回滚

- 不在 ECS 上直接编辑源码。
- Cloud 和 Worker 使用同一不可变镜像 tag，不继续依赖易漂移的 `latest` 作为唯一标识。
- Runner 使用单独不可变 tag。
- 部署前备份 PostgreSQL，并保留上一版 Cloud/Runner 镜像。
- 只重建 VisionOwl Compose 内相关服务，不关闭或占用其他应用端口。
- 健康检查、迁移和冒烟通过后再切换演示客户端。
- 回滚时恢复上一镜像；数据库迁移必须设计为向后兼容。
