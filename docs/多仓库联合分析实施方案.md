# VisionOwl 多仓库联合分析实施方案

## 目标

支持一个 Project 绑定多个仓库及分支，通过并行扫描生成一张包含跨仓库调用关系的完整图谱，同时保持现有单仓库 Project 的行为兼容。

## 数据模型

- 将 `repository_bindings` 从 Project 一对一改为一对多，并以 `project_id + repo_full_name + branch` 去重。
- 为仓库绑定补充稳定的绑定 ID 和主仓库标记，节点通过 `repositoryId` 定位源码仓库。
- 新增仓库扫描子任务，记录每个仓库的 commit、状态、重试次数和扫描产物。
- `analysis_jobs` 保存本次分析的 `repository_commits` 快照。
- `graph_versions` 保存完整的 `repository_commits`，多仓库图谱的 `commit_sha` 使用项目快照哈希。

## API 与前端

- 提供 Project 仓库列表的查询、添加和删除接口，保留旧单仓库绑定接口作为兼容入口。
- 创建 Project 时允许连续添加多个“仓库 + 分支”，确认后统一触发分析。
- Project 详情返回 `repositories` 数组，同时保留首个主仓库作为兼容字段。
- 图谱节点和证据携带 `repositoryId`，Chat 与文档生成按节点所属仓库读取源码。

## 并行扫描

1. Cloud API 创建父分析任务并固定所有仓库的 commit SHA。
2. Worker 为每个仓库创建扫描子任务并写入 Redis Stream。
3. Worker 池消费子任务，每个子任务启动一个临时 Runner。
4. Runner 输出单仓库图谱、Fact Index、接口目录、质量报告和影响面。
5. 子任务产物写入 Artifact Storage，执行状态写入 PostgreSQL。
6. 所有子任务成功后触发一次跨仓库合并；失败子任务单独重试，不重复扫描成功仓库。

## 跨仓库合并

- 使用 `linkProjectRepositories()` 根据 HTTP、RPC、事件 Topic 等双边证据建立跨仓库关系。
- 使用 `composeProjectGraph()` 合并各仓库节点、关系和视图。
- 无法唯一确认的关系保留在 `unresolved`，不写入正式图谱。
- 合并完成后创建新的 GraphVersion，并通过 SSE 通知 Electron 刷新。

## 增量策略

首期保证多仓库全量联合分析正确。后续收到单仓库 Push 时，只重扫发生变化的仓库，复用其他仓库最近一次有效产物，再重新计算跨仓库关系。

## 失败与并发

- Runner 并发受 `WORKER_CONCURRENCY` 控制，不随仓库数量无限增长。
- 仓库扫描默认最多执行三次，最终失败时不发布新的 Project 图谱。
- 合并阶段使用分布式锁，避免多个 Worker 重复发布同一版本。
- 上一版有效图谱在新版本通过全部校验前保持可用。

## 部署顺序

1. 先备份 PostgreSQL 与当前后端源码，再执行新增数据库迁移。
2. Cloud API、Worker 与 Runner 必须使用同一份代码构建；Runner 不得保留旧扫描器镜像。
3. 先构建候选镜像并完成编译，再切换 `visionowl-cloud:latest` 和 `visionowl-runner:latest`。
4. 重建 Cloud API 与 Worker，保留 PostgreSQL、Redis、Nginx 及其数据卷。
5. 使用两个公开仓库创建临时 Project，验证绑定、快照冻结、并行子任务、联合图谱和清理流程。

## 验收标准

- 一个 Project 可绑定至少三个仓库，并可单独删除仓库。
- 每个仓库形成独立扫描子任务和 Runner 执行记录。
- 最终图谱保存所有仓库的 commit，并能追溯节点所属仓库与源码证据。
- 可确认的跨仓库 HTTP、RPC 或 Topic 关系生成正确方向的连线。
- 模糊关系不会被强行连接。
- 任一仓库最终失败时不覆盖上一版图谱。
- Chat 和文档生成能够读取所选节点所属仓库的正确源码。
