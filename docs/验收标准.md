## 0. 这份文档怎么用

四件事:**判定**(唯一断言 + 数值阈值,只判 ✅/❌/⬜)、**记分**(按档结算,见 §5)、**口径**(「性质」列区分实测/目标,答辩引数字先看这列)、**分工**(🤖 无人值守 / 🤝 半自动 / 👤 人工)。

### 0.1 自动与人工的分界

分界不在于能不能写成脚本,而在于 **AI 能不能给自己当裁判**。

L1-4 行号回验可以自动——"第 11 行是不是真有这个符号"是客观事实,脚本验得了,AI 也赖不掉。L2-5 文档过期准确率不行——它的分母("该报的有哪些")得有人工黄金集;让分析器自己列应报清单再跟自己输出比,是循环论证,结果永远 100%。

自动类的输出是**退出码**,人工类的输出是**判断**,两者不能互代。

### 0.2 v2.0 相对 v1.1 改了什么(为什么要改)

v1.1 有 41 条,记分板 4/41 且那 4 条全是环境实测,功能类 0/37。**验收是手段不是目的**——做验收的成本不该超过做功能。四项结构性修改:

| 改动 | 原因 |
|---|---|
| **分 P0/P1/P2 三档**,P0 = **14 条** | 按「答辩拿分 ÷ 实现成本」排序。41 条全做完不现实,砍到能跑完 |
| **新增 G2.5 成本校准 Gate** | v1.1 待定项 #5(credit 熔断)自称"阻塞开跑"。现在把它变成 loop 的第一个实测步骤,用一次可控花费买掉烧穿风险 |
| **G6 安全层拆两半** | v1.1 让 G6 依赖 G3。L4-1/4-4/4-6 根本不需要分析成功——最易拿分的层不该陪最易失败的管线一起死 |
| **L1-4 改用备选归因方案** | 契约 v1.0 已冻结且 Cloud Agent 正在联调,此刻改 evidence 结构会打断联调。`origin` 字段推 v2 |

新增 **R11/R12** 两条元规则(依赖失败记 ⬜、验收区只读机制拦截)。

## 1. 元规则

| 规则 | 说明 |
|---|---|
| **R1 分档独立结算** | P0/P1/P2 独立算分。L0 不依赖分析管线,P1+P3 里程碑完成即可满分 |
| **R2 一条只测一件事** | 断言里出现"且"要警惕,大概率该拆 |
| **R3 阈值实现前定死** | 继承 `test/docs/change-scenarios.md` 的做法(已核实:该文件先于分析器存在)。禁止事后按结果回调 |
| **R4 三态记录,⬜ 不算过** | ✅通过 / ❌不通过 / ⬜未测。禁止"待填""基本通过" |
| **R5 可执行优先** | 验证方式必须是命令、脚本或可逐项勾选的清单。不出现"抽查""目视""美观" |
| **R6 标注性质** | 每个数字标 `实测` 或 `目标` |
| **R7 反向断言配套** | "能做到 X"尽量配一条"不该发生的 Y 没发生"。乱报警的工具没人用 |
| **R8 执行主体二分** | 每条标 🤖/🤝/👤,判定依据见 §0.1 |
| **R9 阈值执行期不可变** | 运行中禁止改阈值、跳过失败条目、改写断言。失败记 ❌ 继续下一条 |
| **R10 失败也归档** | 每个 Gate 结束无论成败都写报告 + 自动 commit。只在通过时存档,失败现场就丢了 |
| **R11 依赖失败记 ⬜** | 上游 BLOCKED 时,下游条目记 **⬜(未测)而非 ❌(不通过)**。记 ❌ 会让记分板虚低,把"没测"说成"不通过",答辩自己吃亏 |
| **R12 验收区只读(机制拦截)** | 本文档与 `accept/gates/` 为只读区。loop 启动记 SHA256,每轮校验,不一致立即 ABORT。这是把"禁止改阈值"从口头约定升级为机制 |

## 4. P2 · 降级为「设计说明」(11 条)

保留在文档里标 ⬜ + "设计已定,未验证",**不投入实现成本**。答辩照实说,留白比硬凑数字诚实。

| # | 摘要 | 降级原因 |
|---|---|---|
| L2-3 | 契约加 currency,影响链 5/5 | 5 条全中太脆,一环断则整条 ❌,信息量低 |
| L2-4 | 文件重命名,孤立文档 = 0 | 与 L2-6 部分重叠,优先级低于 L2-2 |
| L2-5 | 文档过期准确率≥70%/召回≥80% | **统计不成立**:黄金集只在 4 场景内标,分母 5-8 份,±1 份就跨阈值。答辩被问"分母多少"会尴尬。若要保留,改绝对数断言 |
| L3-7 | 增量收益 ≥5× / 成本降 ≥60% | **全表 ROI 最低**:要额外烧一次全量才能对比,而 5× 是拍的 |
| L4-2 | 日志无凭证 | 与 L4-1 同类,边际收益低 |
| L4-4 | 出网白名单生效 | 依赖 runner-net 配置就绪 |

| L4-7 | 审计完整(5 类操作) | 实现量大,答辩价值低 |
| H-1 | 节点摘要语义正确 ≥13/15 | 见下方说明,**若有人力应升 P1** |
| H-2/4/5 | 推断合理性 / 视觉契约 / 控制台三态 | 主观项,H-6 已覆盖演示效果 |

**H-1 的特殊性(唯一建议破格上调的)**:核心卖点是"每条结论能点开看到代码哪一行",而自动层只验得了一半——

```
L1-4 能验:文件存在吗?行号越界吗?符号真在区间内吗?   ← 形式真实
H-1  才能验:这段代码真的在干 summary 说的那件事吗?    ← 内容正确
```

一个完全能通过 L1-4 的反例:节点 `modules/payment` 的 evidence 指向 `payment-gateway.ts:1-13`,文件真存在、行号不越界、符号也对,但 summary 写成"处理退款对账"——**行号全对,结论张冠李戴,脚本抓不到**。抽 15 个、**≥13 相符**(写绝对数避免小数争议),一人半小时能完。**有半小时人力就做。**

## 6. 无人值守执行规约

### 6.1 Gate 划分(v2.0 调整)

| Gate | 内容 | credits | 前置 |
|---|---|---|---|
| **G0** 环境自检 | 容器健康、DB 连通、`ARTIFACTS_DIR` 可写、git 工作区干净、**验收区 hash 基线记录(R12)** | 0 | 无 |
| **G1** 认证与权限 | L0-1 L0-2 L0-3 L0-7 L0-8①② | 0 | G0 |
| **G2** 图谱只读链路 | L0-4① + `协同开发.md §12 CP2` 等价断言 | 0 | G1 |
| **G2.5** ⭐**成本校准** | 对 fixture 跑 **1 次**全量,读实际 credits → **重算 G3/G4 预算与熔断线** | ~1 次全量 | G2 |
| **G3** 全量分析 | L1-1 L1-2 L1-3 L1-4 (L1-5) | 按 G2.5 校准 | G2.5 |
| **G4** 增量与场景 | L1-6①② L2-2 (L2-1 L2-6) | 按 G2.5 校准 | G3 |
| **G5** 成本与效能 | L3-5/6 (L3-8/9) | 读埋点日志,不额外烧 | G4 |
| **G6a** 安全(**不依赖分析**) | L4-1 (L4-4 L4-6) | 0 | **G0** |
| **G6b** 安全(依赖跑过一次任务) | L4-3 | 0 | G2.5 |

括号内为 P1 条目,P0 全绿后才放开。

**G2.5 是 v2.0 最重要的新增**:v1.1 待定项 #5 自称"阻塞开跑",本质是**单价基线不成立**——E-2 的 10.36 credits 是 express `lib/` 6 节点,而 EventHub fixture 是 17 节点 + 更深依赖,单次全量很可能远超预估。第一次 G3 就超预算 → 整个 loop ABORT → **收益 0**。用一次可控花费买掉这个风险。

```
G2.5 判定与动作:
  实测单次全量 = C credits
  C ≤ 60   → G3 上限 = 3C,G4 上限 = 4C,全局 = 8C
  C > 60   → 缩小分析范围(只扫 modules/ + packages/)后重测一次
  重测仍 >60 → 标 BLOCKED,G3/G4 全部 ⬜(R11),转人工决策
```

**G6a 独立于分析管线**:即使管线全线失败,安全层仍有条目能绿。

### 6.2 每个 Gate 的固定动作(R10,无论成败)

```bash
# 1. 结构化报告(每条含 断言/期望值/实际值/判定/耗时)
accept/reports/G3-20260804T1130Z.json
accept/reports/G3-20260804T1130Z.md      # 人看的版本

# 2. 自动 commit,通过数写进 message,失败逐个列出
git add accept/ && git commit -m "accept: G3 3/4 passed (failed: L1-4)"

# 3. 打 tag 便于回滚对比
git tag accept-g3-20260804T1130Z
```

commit 前缀 **`accept:`**,只动 `accept/` 目录,不碰两端代码,与 `协同开发.md §1` 的目录隔离不冲突。需在该文档补登这个前缀(约定新增,非接口契约变更)。

### 6.3 自动开发 loop(验收 loop 的孪生)

同一套闸门反向用作开发驱动。**41 条 ⬜ 天然是任务队列**——每条有唯一断言 + 阈值,正是"完成定义"。

```
driver(哑脚本,不含智能)
  读 state.json → 挑一条 ⬜ → 组装窄 prompt
      ↓
  qodercli -p --max-turns 25 --permission-mode accept_edits   ← 一轮只做一条
      ↓
  快闸 tsc/lint/单测/schema          秒级 · 0 credit
      ↓ 绿
  中闸 契约 curl CP / DOM 断言 / G6a  分钟级 · 0 credit
      ↓ 绿
  慢闸 真实分析管线                   烧 credit · 查累计后放行
      ↓
  判定 → 更新 state → commit(回滚点)→ 追加报告
      ↓
  下一条 | 同条失败 3 次 → BLOCKED 跳过 | 超预算 → ABORT
```

四条设计原则:

| 原则 | 理由 |
|---|---|
| **一轮一条** | R2 的对偶。一轮改多处,失败无法定位,回滚粒度也没了 |
| **driver 是哑脚本,agent 每轮新起会话** | 不要"一个 agent 跑 8 小时"——上下文越长漂移越严重。prompt 只塞这一条的断言 + 相关文件 + 闸门命令 + 禁止事项 |
| **闸门按成本递增** | 快闸拦掉大部分低级错误,不让烂代码浪费 credit 走到慢闸 |
| **每轮 commit** | 不 commit 的 loop 跑歪一次,整夜工作全废 |

目录形态:

```
accept/
├── state.json          当前任务/轮次/累计credit/各条状态   ← 唯一可写状态
├── tasks.jsonl         由本文档生成的任务队列              ← 只读
├── gates/{fast,mid,slow}.sh                              ← 只读(R12 校验)
├── reports/G*.{json,md}
├── manual/             人工验收输入(由 loop 准备)
└── loop.sh             driver(约 120 行 bash)
```

### 6.4 防作弊(自动开发的头号风险)

Agent 让闸门变绿最省事的办法是**改闸门**。必须机制性禁止,不能只靠 prompt 里写"不许改":

1. **只读区 hash 校验(R12)**:G0 记录本文档 + `accept/gates/` 的 SHA256,每轮比对,不一致 → 立即 ABORT 保留现场
2. **commit 前置检查**:diff 若触及阈值行(正则 `≥\d|=\s*0|≤\d`)直接拒绝提交
3. **反向断言配套(R7)**:实现 X 时必须同时验"Y 没被破坏",防止为过一条而砸坏别的
4. **成本账本独立记**:credits 从 `analysis_jobs.credits` 读(数据库事实),**不信 agent 自报**

### 6.5 禁止事项(无人值守期)

- ❌ 任何形式的 `git push`。只本地 commit,推送等人工看过报告后手动做
- ❌ `push --force` / `reset --hard` / 改写历史 / 删分支(除自建 `accept/scenario-*`)
- ❌ 修改 master 上的 `test/` `app/` `visionowl/` 与现有 skill(除新增 `visionowl-graph`)
- ❌ 删除或重建 `infra-postgres-1` 数据卷
- ❌ 修改本文档任何阈值或断言(只能填「状态」列)
- ❌ 超过 credit 上限后继续跑
- ❌ 把 👤/🤝 类条目自行判 ✅(包括"看截图觉得没问题"),只能置 ⬜ 转人工

**最后一条单独强调:验收的 AI 不得代替人判定人工条目。** 它可以准备现场(启客户端、加载恶意 fixture、截图存 `accept/manual/`),但判定权在人。

### 6.6 场景验证用影子工作树

真实矛盾:L2 场景要改 `test/` 里的代码,而 `协同开发.md §1` 明令 `test/` 禁止修改。解法:

```bash
git worktree add /tmp/accept-s2 -b accept/scenario-2 HEAD
#   …在 /tmp/accept-s2/test/ 里改代码、跑分析、比断言…
git worktree remove --force /tmp/accept-s2
git branch -D accept/scenario-2          # 场景分支跑完即弃
```

报告里记下每个场景的临时分支 SHA,人工复查时能重建现场。
