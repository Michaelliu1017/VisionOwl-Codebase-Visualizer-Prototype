# Knowledge Generator 实施与部署方案（已验证）

## 1. 目标与结果

Knowledge Generator 是 VisionOwl 的独立知识沉淀模块，已经完成两条可单独验证的链路：

1. 独立采集：输入公开 GitHub 仓库，采集 Commit、PR、Review、Comment、CI、Job 和文件变更，输出 Evidence v1 证据图。
2. 主模块集成：消费 Redis 的 knowledge:tasks，读取冻结版本的代码图谱，将工程证据连接到代码模块，生成可直接使用的 Wiki 和 Skills，再把产物回传 VisionOwl Core。

模块不导入主模块代码，不读取主模块数据库。双方只通过 Redis 消息和带服务令牌的 HTTP API 交互，因此主模块未启用知识功能时仍可正常运行。

## 2. 最终架构

独立采集链路：

GitHub API → Raw Record → Evidence Normalizer → Evidence Linker → Validator → Evidence Graph

完整知识链路：

VisionOwl Core → Redis knowledge:tasks → Knowledge Worker → 冻结代码图谱 + GitHub Evidence → 模块建联 → 知识生成 → Wiki/Skills/Manifest/ZIP → Core Artifact API

职责边界：

| 组件 | 职责 |
| --- | --- |
| GitHub Client | 分页读取仓库、Commit、PR、Review、Comment、Actions 和 Job，处理限流与重试 |
| Sync Orchestrator | 组织首次或增量采集，维护来源、状态和快照 |
| Normalizer | 将 GitHub 对象转换成平台无关的 Evidence v1 节点 |
| Evidence Linker | 根据 GitHub ID、完整 SHA、PR 编号和文件路径建立确定性关系 |
| Validator | 检查 Schema、重复对象、悬空关系和来源完整性 |
| Knowledge Linker | 按仓库、冻结 Commit 和文件路径把证据连接到代码模块 |
| Semantic Analyzer | 默认生成确定性知识；可选 Qoder 做有证据约束的语义增强 |
| Publisher | 生成独立文件、Manifest、ZIP 和 SHA-256，并上传 Core |
| Knowledge Worker | 可靠消费 Redis Stream，执行任务、回报进度并处理重试 |

## 4. 从零运行

### 4.1 前置条件

- Node.js 22 或更高版本。
- 可访问 GitHub API。
- 一个只读 GitHub Token。公开仓库也建议配置，否则匿名额度很快耗尽。
- 只有接入主模块时才需要 Redis 和 VisionOwl Core。

不要把 Token 提交到 Git。只写入本机 .env 或部署环境的受限配置文件。

### 4.2 安装与自检

进入目录：

cd /Users/你的用户名/项目路径/alitest/knowledge-generator

未安装 pnpm 时直接使用：

npx --yes pnpm@11.16.0 install

复制环境模板并填写 GITHUB_TOKEN：

cp .env.example .env

执行类型检查和全部测试：

npx --yes pnpm@11.16.0 check

验收要求：typecheck 成功，全部单元测试和集成测试通过。

## 5. 使用 Fastify 做真实采集测试

测试仓库：

https://github.com/fastify/fastify

建议先限制时间和数量，确认闭环后再扩大范围：

npx --yes pnpm@11.16.0 run sync -- --repo https://github.com/fastify/fastify --project-id fastify-test --since 2026-01-01T00:00:00Z --max-items 100 --concurrency 3 --data-dir /private/tmp/fastify-evidence

成功时命令输出满足：

- run.status 为 succeeded。
- rawRecords、nodes、edges 和 apiRequests 大于 0。
- snapshotPath 指向生成的 evidence-graph-版本号.json。
- pendingLinks 应为 0；若不为 0，需要检查缺失的目标对象。

找到最新稳定快照：

SNAPSHOT=$(find /private/tmp/fastify-evidence/snapshots -name evidence-graph.json -print -quit)

执行 Schema 与关系校验：

node --import tsx src/cli.ts validate --snapshot "$SNAPSHOT"

查看采集类型和关系：

jq '.stats.nodesByKind, .stats.edgesByType' "$SNAPSHOT"

Fastify 数据持续变化，不应比较固定数量。验收重点是 Commit、change_request、review、comment、ci_run、ci_job、file 和 file_change 等核心类型存在，并且 PR、Commit、Review、CI 与文件关系能够连接。

## 6. 统一 Evidence 模型

每个 Evidence 节点至少保留：provider、repositoryId、kind、externalId、state、actor、commitSha、occurredAt、sourceUrl、rawRef 和 checksum。

关键关系全部使用平台明确字段建立：

| 关系 | 依据 |
| --- | --- |
| PR_CONTAINS_COMMIT | PR Commits API |
| PR_HAS_REVIEW | Review 所属 PR |
| PR_HAS_COMMENT | Issue Comment 所属 PR |
| REVIEW_HAS_COMMENT | pull_request_review_id |
| COMMENT_TARGETS_FILE | path、line、side |
| COMMIT_CHANGES_FILE | Commit Files API |
| COMMIT_PARENT_OF | Commit parents |
| CI_VALIDATES_COMMIT | Workflow Run head_sha |
| CI_CONTAINS_JOB | Job run_id |
| PR_MERGED_AS_COMMIT | merge_commit_sha |

禁止根据标题相似、作者相同或自然语言猜测关系。目标节点暂时不存在时写入 pending link，不能制造悬空边。

## 7. 接入 VisionOwl Core

### 7.1 Core 配置

主模块环境至少配置：

KNOWLEDGE_INTEGRATION_ENABLED=true

KNOWLEDGE_AUTO_GENERATE=false

INTEGRATION_SERVICE_TOKEN=长度至少32字节的随机令牌

关闭自动生成时，用户通过工程知识资产面板的刷新按钮手动触发，便于控制 GitHub 配额和生成成本。

### 7.2 Knowledge Generator 配置

Knowledge Generator 的 .env 至少配置：

KNOWLEDGE_WORKER_ENABLED=true

REDIS_URL=redis://redis:6379

CORE_BASE_URL=http://cloud:17800

CORE_SERVICE_TOKEN=与Core的INTEGRATION_SERVICE_TOKEN完全相同

GITHUB_TOKEN=只读GitHub令牌

KNOWLEDGE_SEMANTIC_PROVIDER=deterministic

首次联调建议使用：KNOWLEDGE_HISTORY_DAYS=30、KNOWLEDGE_MAX_ITEMS=20、GITHUB_MAX_CONCURRENCY=2、KNOWLEDGE_REPOSITORY_CONCURRENCY=1。

### 7.3 运行时协议

1. Core 创建 Knowledge Run，并将 runId 写入 knowledge:tasks。
2. Worker 使用 Consumer Group 拉取消息。
3. Worker 调用 /internal/v1/knowledge-runs/:runId/command 获取冻结命令。
4. Worker读取同一 GraphVersion 和各仓库固定 Commit。
5. Worker采集证据、建联、生成资产并上传。
6. Worker调用 progress、complete 或 fail 回调。
7. 成功或已确认失败后 ACK；Core 暂时不可达时保留 Pending，由 XAUTOCLAIM 重试。

内部请求必须使用 x-visionowl-service-token 请求头，不能使用普通用户 Bearer Token。

## 8. ECS Docker 部署

当前已验证部署目标：/opt/vo/knowledge-generator

### 8.1 上传源码

在 alitest 目录执行以下命令，可避开受限环境中的 scp：

tar -czf - --exclude=node_modules --exclude=dist --exclude=data --exclude=.env knowledge-generator | ssh -i 密钥.pem root@ECS地址 'mkdir -p /opt/vo && tar -xzf - -C /opt/vo'

### 8.2 准备环境

在 ECS 复制模板：

cd /opt/vo/knowledge-generator

cp .env.example .env

编辑 .env，并设置为仅 root 可读：

chmod 600 .env

确认主模块 Docker 网络存在：

docker network inspect infra_visionowl-private

### 8.3 重启 Core

修改 /opt/vo/infra/.env 后执行：

cd /opt/vo/infra

docker compose -p infra -f compose.yaml up -d --no-deps --force-recreate cloud worker

### 8.4 构建并启动 Knowledge Worker

cd /opt/vo/knowledge-generator

docker build --build-arg NODE_IMAGE=node:22-slim -t visionowl-knowledge-generator:latest .

docker compose -p knowledge-generator -f deploy/compose.ecs.yaml up -d --no-build

该服务不开放公网端口，只连接 infra_visionowl-private，通过 redis:6379 和 cloud:17800 与主模块通信。

## 9. 部署验收

查看容器：

docker compose -p knowledge-generator -f /opt/vo/knowledge-generator/deploy/compose.ecs.yaml ps

查看日志：

docker compose -p knowledge-generator -f /opt/vo/knowledge-generator/deploy/compose.ecs.yaml logs -f

日志应出现：consuming knowledge:tasks as knowledge-generators/消费者名称。

检查 Redis Consumer Group：

docker exec infra-redis-1 redis-cli XINFO GROUPS knowledge:tasks

应看到 knowledge-generators，空闲时 pending 为 0、lag 为 0。

最终验收标准：

- Knowledge Generator 容器持续 running，重启次数为 0。
- GitHub API 请求返回 200，认证额度通常为每小时 5000 次。
- 使用正确服务令牌访问不存在的 /internal/v1/knowledge-runs/UUID/command 返回 404，说明认证和路由均已命中；返回 401 表示请求头或令牌不一致。
- 在 VisionOwl 中完成代码图谱后触发知识刷新，任务依次经过采集、建联、生成和发布。
- 工程知识资产面板出现 Wiki 和 Skills，并能下载对应产物。

## 10. 产物与存储

生成内容包括 Wiki、模块文档、开发规范、踩坑指南、Skills、Manifest、traceability 和 ZIP Bundle。首次生成的 Skill 直接发布；同一项目后续生成的新 Skill 版本作为候选进入 Skill Lab 评估与优化。

当前 Demo 部署未接入 OSS：

- 最终产物由 Core 保存到 ECS 的 /data/artifacts。
- Knowledge Generator 中间快照保存在 knowledge-generator_knowledge-data Volume 的 /app/data。
- PostgreSQL 只保存任务、版本、状态、路径和校验值等元数据。

正式环境应将最终大文件迁移到 OSS，并将数据库迁移到 RDS PostgreSQL；这不会改变 Worker 与 Core 的接口。

## 11. 实际踩坑与处理

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 本机没有 pnpm | 未安装全局 pnpm | 统一使用 npx --yes pnpm@11.16.0 |
| GitHub API 403，等待时间很长 | 匿名额度耗尽或触发限流 | 配置只读 GITHUB_TOKEN，并降低并发和 max-items |
| Core 返回 401 | 路径、请求头或令牌不一致 | 使用 /internal/v1 路径和 x-visionowl-service-token，并确保两端令牌相同 |
| 生产 Core 启动失败 | 集成令牌过短 | INTEGRATION_SERVICE_TOKEN 至少32字节 |
| Compose 找不到网络 | 主模块私有网络不存在或名称错误 | 先启动 infra，确认 infra_visionowl-private 存在 |
| Docker 内找不到 Qoder | 默认镜像不包含 Qoder CLI 和个人凭证 | 先使用 deterministic；需要语义增强时制作专用镜像 |
| 大仓库首次采集过慢 | 历史范围和对象数过大 | 先用30天、20项、并发1至2完成冒烟测试，再逐步放大 |

## 12. 完成定义

满足以下条件即认为模块可以交付：

1. 本地 check 全部通过。
2. Fastify 真实采集成功，Evidence Graph 校验通过且核心对象与关系存在。
3. ECS Worker 正常消费 knowledge:tasks，无持续 Pending 或重启。
4. Wiki、Skills、Manifest 和 ZIP 成功回传 Core，首次生成不依赖 Skill Lab。
5. 每条知识能够追溯到 Evidence ID、GitHub URL、Commit 和代码模块。
6. Knowledge Generator 停止时，VisionOwl 原有代码扫描、图谱和协作功能不受影响。
