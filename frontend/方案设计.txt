# 拨测闭环可视化系统方案设计

## 项目简介

拨测可以理解为让分布在不同地域的探针定期访问网站或接口，模拟真实用户请求，从而判断服务是否可访问、响应是否变慢。一次拨测并不是探针直接访问目标这么简单，任务还需要经过创建、调度、下发、执行、结果上报和日志存储等多个环节。

本项目要建设一个拨测闭环可视化系统，把 Worker、Agent-Rest、GoProbe、MySQL、Redis 和 SLS 等组件放在同一张动态拓扑图中。用户可以看到系统中有多少个组件正在运行、任务目前经过了哪个节点，以及探测结果最终写到了哪里。

正式系统将建立在 UModel 之上，利用 UModel 对拨测组件、探针、任务、存储和目标服务进行统一实体建模，并用实体关系描述注册、调度、任务下发、探测和结果上报链路。前端根据 UModel 中的实体、关系和状态数据生成拓扑，而不是在页面中写死组件之间的连接。

比赛阶段的重点是验证产品形态和交互方式，暂不接入真实 UModel 与生产拨测数据。Demo 将使用遵循相同实体和关系模型的 Mock 数据，模拟组件状态与事件流转，从而完整展示未来接入真实数据后的使用效果。

## 解决的工作痛点

- 系统链路较长，新参与者需要阅读多个仓库和文档才能理解一次拨测如何完成。
- 运行信息分散在进程、Redis、MySQL、组件日志和 SLS 中，排查时需要在多个系统之间反复切换。
- 任务没有执行时，很难快速判断问题发生在 Worker 调度、Agent-Rest 下发、GoProbe 探测还是结果上报阶段。
- 只能看到最终拨测结果，无法直观观察任务在各组件之间的实时流转过程。
- 故障发生后缺少统一入口，组件状态、链路证据和 Agent 根因分析无法放在一起查看。

该系统通过动态拓扑、节点详情和事件时间线集中呈现这些信息，降低拨测系统的理解和排障成本，并为后续接入 StarOps Agent 自动诊断提供可视化入口。

## 一、背景

拨测任务会依次经过任务创建、调度、任务下发、探针执行、结果上报和日志存储。当前这些状态分散在进程、MySQL、Redis、Agent-Rest 日志和 SLS 中，使用者难以快速判断任务卡在哪个环节，也不容易理解各组件之间的关系。

## 二、目标

建设一个拨测闭环可视化系统，将 TaskCenter、Worker、Agent-Rest、GoProbe、MySQL、Redis 和 SLS 展示在同一张动态拓扑图中，使用户能够：

- 查看当前 Worker、Agent-Rest、GoProbe 和任务队列状态。
- 观察任务从创建到执行、上报和落盘的完整过程。
- 点击节点查看实例、任务、队列和运行参数。
- 在异常发生时快速确定故障位于调度、下发、探测还是上报环节。

## 三、整体链路

任务运行的主链路为：

Console → TaskCenter → MySQL / Redis → Worker → Execution Queue → Agent-Rest → GoProbe → 目标站点

结果上报链路为：

GoProbe → Agent-Rest → reports.ndjson / SLS Logstore

GoProbe 启动后还会向 Agent-Rest 注册。Agent-Rest 将探针信息写入 MySQL 和 Redis AgentCache，Worker 根据 AgentCache 确定任务需要投放到哪条执行队列。

## 四、前端设计

页面由四部分组成：

1. 顶部状态栏：展示 Worker、Agent-Rest、GoProbe、待执行任务和报告数量。
2. 闭环拓扑图：展示组件关系，并用动态流光表示当前事件的传递方向。
3. 节点详情面板：展示选中节点的地址、端口、Client ID、任务数量和健康状态。
4. 事件时间线：按顺序记录注册、调度、拉取、探测、上报和存储事件。

视觉上沿用 CodeTopo 风格，使用黑色背景、深灰色实体节点和荧光绿色正常链路；受影响节点使用橙色，明确故障节点使用红色。

## 五、数据设计

正式方案以 UModel 为统一建模层：

- 实体表示 Worker、Agent-Rest、GoProbe、任务、队列、存储和被探测目标。
- 关系表示注册、管理、调度、下发、执行、上报和写入等连接。
- 运行事件为实体和关系补充时间、状态、任务 ID、Client ID 与异常摘要。

比赛 Demo 使用与上述模型一致的前端 Mock 数据，验证页面结构、事件动画和交互逻辑，不连接真实 UModel，也不修改 M5 后端。

后续由后端聚合各组件的运行状态，并通过 WebSocket 或 SSE 向页面持续推送统一事件。每条事件至少包含事件类型、时间、来源节点、目标节点、任务 ID、Client ID、状态和摘要信息。前端只负责根据事件更新节点、连线和时间线。

## 六、实施阶段

- 第一阶段：完成纯前端 Demo，验证拓扑布局、事件动画和节点交互。
- 第二阶段：接入 M5 本地闭环的真实 Worker、Agent-Rest、GoProbe、Redis 和 MySQL 状态。
- 第三阶段：接入异常告警与 StarOps Agent 分析，用户点击故障节点即可查看根因和处理建议。
